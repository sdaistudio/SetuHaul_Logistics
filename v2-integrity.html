FDE ACADEMY | MINI PROJECT 2 | SETUHAUL LOGISTICS

Deliverable 5

Integrity Proof

Evidence that competing requests cannot double-book a dock: five defence layers, twelve tests, a ten-driver race repeated fifty times, and negative controls that show the test can fail

The claim is that no slot, no shipment and no minute of dock time is ever promised twice, whatever the timing of messages, retries or coordinator actions. Below are the threats, the layer that stops each one, the tests that attack each layer, and their results from the run shipped with the prototype. All 12 tests pass. In 50 races of 10 drivers each, every race had exactly one winner, 450 drivers got a clean refusal, and no raw error reached a driver.

Client: SetuHaul Logistics Pvt. Ltd. (FDE Academy challenge)

Snapshot: 4 August 2026, Jaipur DC and Gurugram Cross-Dock (Asia/Kolkata)

Version: 1.0 | 18 November 2026

Audience: FDE Academy reviewers; SetuHaul engineering lead and head of operations

1. The claim, and the verdict

DECISION | What we claim

At any moment, each slot has at most one live booking or hold, each shipment has at most one current booking, no two trucks are promised overlapping time on one door, and every booking respects the door's type and weight limit. This holds under simultaneous requests, retries, stale options, coordinator approvals and swaps.
Evidence Result
12 integrity tests (section 5) 12 passed, 0 failures, 0 errors (1.5 s)
10 drivers, one slot, the same instant, repeated 50 times 50 of 50 races had exactly one winner; 450 clean refusals; 0 raw errors leaked; 0 double bookings; 10 different shipments won across the 50 runs
Negative control: the same race with the guards removed 10 of 10 drivers booked the same slot, in each of 5 runs
Negative control: supplied unique index only, no transaction 1 booked, 9 raw database errors that a driver would have seen, in each of 5 runs
Random stress: 8 threads x 25 random bookings 200 requests: 45 confirmed, 143 refused (option gone), 12 sent for approval, 0 errors, 0 invariant violations
Scenario run (deliverable 4) 4 invariants checked on the final database: all 0

IN PLAIN WORDS | What "exactly one winner" means

Think of ten people pressing a lift button at the same moment for a lift that fits one. The building must let exactly one in, and tell the other nine politely that it is full, not show them an error screen. Fifty times in a row, that is what happened.

2. How a double booking can happen

# Threat Real example from this data Layer that stops it
T-a Two drivers pick the same slot at the same time 09:36: DRV013 and DRV006 both pick D4 12:40 1 (one write lock) + 2 (unique index)
T-b A driver's tap is delivered twice (network retry, webhook redelivery) WhatsApp retries; THR009 duplicates THR001 5 (idempotency key, dedupe)
T-c An option is shown, then the world changes before the pick D3 breaks down at 09:15 1 (re-check inside the transaction)
T-d A slot is held for a coordinator and offered to someone else SHP1020's evening slot held at 09:33 3 (hold indexes) + 1
T-e A long unload runs into the next slot on the same door A 75-minute unload in a 60-minute slot (F05) 4 (overlap trigger)
T-f A truck still unloading past its expected end SHP1002 overran D2 by 10 minutes 1 (busy intervals include overruns) + 4
T-g A coordinator approves after the world changed Maintenance added while a hold waits 1 (approval re-checked)
T-h A swap moves one booking but fails to move the other CRITICAL load swapping with a NORMAL load 1 (both moves in one transaction)
T-i A bug in the feasibility code A future change forgets a busy interval 4 (database triggers do not trust the code)
T-j Another system writes to the database directly The client's planner tool inserts a booking 2 + 4 (constraints apply to every writer)
T-k An active booking escapes the per-shipment index is_current = 0 on an active row (audit F09) 4 (trg_active_must_be_current)

3. Five layers of defence

Layer What it is Where What it guarantees on its own
1. One transaction BEGIN IMMEDIATE takes the write lock before the re-check; check and insert happen with no gap between them db.write_txn, capacity.commit No interleaving of "check" and "insert" between two writers
2. Supplied unique indexes One active booking per slot; one current active booking per shipment Client schema Even a buggy writer cannot put two active bookings on one slot
3. Hold indexes Partial unique indexes on live holds: one per slot, one per shipment slot_holds A slot waiting for a coordinator cannot be held twice
4. Triggers trg_no_overlap (time on a door), trg_appt_guard (site, type, weight, status, shipment state), trg_active_must_be_current db.py The database refuses an unsafe row whatever code wrote it
5. Idempotency and dedupe Commit result stored under the driver's message ID; duplicate inbound messages suppressed idempotency_keys, inbound_messages A retried request returns the first answer instead of booking again

IN PLAIN WORDS | Why five layers and not one

A bank vault has a guard, a lock, a camera and an alarm. Any one might fail on a bad day; all four failing together is very unlikely. Layer 1 is the guard who checks everything; layers 2 to 4 are locks that work even if the guard is wrong; layer 5 makes sure that pressing the button twice opens one account, not two.

7. Negative controls and stress

Why negative controls. A race test that always passes may simply never have raced. So we ran the same ten drivers with the classic bug: read "is the slot free?", pause 50 ms (the time a real request spends elsewhere), then insert, with no transaction.

Configuration Runs Booked per run Raw errors per run
No unique indexes, no transaction 5 10 (every driver "booked" the slot) 0
Supplied unique indexes, no transaction 5 1 9
Our capacity layer (T01 and the 50 repeats) 51 1 0

The middle row is the situation the client's schema is in today: the index prevents the double booking, but nine drivers would get a database error instead of a reason and fresh options. Our layer turns those nine errors into nine useful replies.

Stress. Eight threads each made 25 random booking requests for Jaipur shipments against open slots after 11:00, all at as-of 09:45. In the recorded run: 45 confirmed, 143 refused because the option had gone or never fitted, 12 sent for approval, 0 errors. The split changes from run to run with thread timing; the invariants were 0 in every run.

8. Running the same proof on Postgres

The production design (deliverable 3, section 9) moves the system of record to managed Postgres. The proof must be re-run there, because SQLite's single writer makes some races easier to win than they will be in production.

Step What we do Pass condition
1 Apply the Postgres DDL: EXCLUDE USING gist on dock time, partial unique indexes on holds, the guard triggers in PL/pgSQL Schema loads; supplied data passes the constraints, or fails only on rows already known to be bad (F08)
2 Point the capacity layer at Postgres; the commit takes pg_advisory_xact_lock(hashtext(facility_id)) before the re-check T01-T12 pass unchanged
3 Run the 10-driver race 50 times with a connection pool of 20 50 single winners; 0 leaked errors
4 Run the race without the advisory lock The exclusion constraint still prevents overlap; refusals appear as typed errors, not raw ones
5 Run two facilities at once (Jaipur and Gurugram races in parallel) No cross-facility blocking; both single winners
6 Add T13: a writer outside our code inserts an overlapping booking Refused by the exclusion constraint
7 Run the suite in CI on every change to capacity.py, timeline.py or the DDL A failing race blocks the release

FDE NOTE | Why step 4 matters

The advisory lock is our "guard"; the exclusion constraint is the "lock on the door". Removing the guard on purpose shows the door is still locked. This is the same idea as the negative controls in section 7.

9. Honest limits

  • One engine tested. All results above are on SQLite 3.53.1. Section 8 is a plan, not a result.

  • One process. The threads share one machine. Multi-machine timing (network delay between workers) is covered only by the Postgres plan.

  • Time is a code rule, not a database rule. "Do not book a slot that has ended" is enforced in the transaction's re-check, not by a trigger, because the database does not know what "now" is in a replay. Production can add a CHECK (start_ts > now()) style trigger on insert.

  • Dock events must be in the database to be respected. A breakdown reported only by phone is invisible until someone records it. The coordinator console makes that one click (deliverable 3).

  • The supplied data already contains a double booking in its history (APT1012A and APT1007 on SLOT-JAI-003, audit F08). Our layers prevent new ones; they do not rewrite history. The appointment_events table makes any future one visible.

10. Reproduce it

Results are written to out/integrity_results.json; the file shipped in the zip is the run quoted in this document.

RACE_REPEATS=500 python3 -I run_integrity.py out/ # a longer soak
